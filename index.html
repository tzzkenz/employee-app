Why We Test

Historic Lesson: The Y2K Bug

1. The Issue

Years recorded as two digits caused failures on January 1, 2000.

2. The Risk

Systems misread 2000 as 1900, leading to calculation errors across banking, aviation, utilities.

3. The Fix

Extensive testing and updates prevented widespread disruption.

Organisations spent an estimated $200–$600 billion on Y2K compliance — almost all of it on writing and running tests against scenarios nobody had thought to test for thirty years earlier.

What is Testing? — The Pile-Up Problem

Day 1

Initially everything is small. One route, one model, one dev who remembers every line.

  • POST /employees
  • 10 lines of business logic
  • "I'll just check it manually"

Six months later

Auth, roles, departments, addresses, audit log, soft delete, search…

  • Every feature touches code paths from every other feature.
  • "Did the email change break login?" — nobody knows.
  • Manual testing alone now takes longer than the change itself.

Tests don't slow you down — they're what lets you keep going at speed when the codebase grows.

“Why smash the whole car when you only need to test the airbag?”

When building a car, the airbag system is just one critical component that needs to function perfectly on its own — before the entire vehicle comes together.

Testing the Airbag in Isolation — with a Mock

Objective

Mock Input

Simulate crash sensor signals by injecting a mocked CrashSensor. No real collisions.

Controlled Setup

Test harness only — no physical car, no risk. Faster, safer, repeatable.

Verification Focus

  • Assert the igniter trigger method is called.
  • Check correct force and timing parameters.
  • Ensure no accidental deployments.

Why It Matters

  • Catches defects at the unit level before integration.
  • Speeds up feedback loops & debugging.
  • Reduces cost & complexity vs. full-system tests.

Same idea, our codebase: we'll test auth_service.login() without spinning up a real database, by replacing the repository with a mock — you'll see exactly this pattern later in the session.

🧪 Why Unit Testing Matters

🐛 Catch bugs early

Detect issues at the smallest level — before they snowball into bigger problems in integration or production.

⚡ Fast & clear feedback

Get immediate insight into what broke and why, right after a change — not three days later in QA.

📚 Living documentation

Pytest Basics

Do We Even Need a Testing Tool?

Tests are just code. In theory, you could write a few if checks and call it a day. Let's see what that looks like.

Without a tool
# my_check.py
from auth.utils import hash_password

if hash_password("abc") == "abc":
    print("FAIL: hash equals input")
else:
    print("OK")

# run: python my_check.py
What we’ll get with a tool
# tests/test_auth_utils.py
def test_hash_does_not_equal_input():
    assert hash_password("abc") != "abc"

# run: pytest

The hand-rolled version works for one check. Once you have a hundred, you need answers to: How do I run only the failing ones? Where do I share setup? How do I see why something failed? How do I run them in CI? A testing tool answers all of these out of the box, and turns "is my code correct?" from a manual chore into a one-command yes/no.

Python Testing Tools — and Why Pytest

Python has a few testing libraries. The two that matter most are unittest and pytest.

ToolWhere it comes fromWhat it’s good for
unittestBuilt into the Python standard library — no install.Tiny scripts; codebases that already use it.
pytestThird-party, but the de facto standard.Almost every modern Python project. This is what we use.
nose2Third-party, older.Legacy projects only.
doctestBuilt-in. Tests inside docstrings.Tiny doc-style examples, not real test suites.
Same test in unittest
import unittest

class TestMath(unittest.TestCase):
    def test_add(self):
        self.assertEqual(1 + 1, 2)
Same test in pytest
def test_add():
    assert 1 + 1 == 2

Why pytest wins for new projects: no class boilerplate, plain assert with automatic failure messages, reusable setup via fixtures, one decorator to run a test on many inputs, and a huge plugin library (coverage, async, parallel, …). Same things unittest can do — with much less code.

Install & Run

Pytest is a development-time dependency. It belongs in pyproject.toml — the single file that describes our project, its dependencies, and its tooling.

# pyproject.toml — what we added for testing
[dependency-groups]
dev = [
    "pytest>=8.0.0",           # the test runner
    "pytest-cov>=5.0.0",       # coverage plugin
    "httpx>=0.27.0",           # required by FastAPI's TestClient
]

[tool.poe.tasks]               # short aliases (uv run poe <name>)
test       = "pytest"
"test:cov" = "pytest --cov=. --cov-report=term-missing"

Install

# installs everything in [dependency-groups].dev
uv sync --group dev

Run

uv run pytest               # quiet
uv run pytest -v            # list each test
uv run pytest -k "login"    # keyword filter
uv run pytest -x            # stop on first failure
uv run pytest --lf          # re-run last failures

uv run poe test             # Poe alias
uv run poe test:cov         # with coverage

Why [dependency-groups].dev and not [project].dependencies? Test tools are only needed during development — not when the API is deployed to production. Keeping them in dev means production installs are smaller and faster.

How Pytest Finds Tests — and How We Tune It

Pytest discovers tests by convention: file names, class names, function names. The [tool.pytest.ini_options] table in pyproject.toml is where we adjust those conventions and the runner behaviour.

# pyproject.toml
[tool.pytest.ini_options]
testpaths      = ["tests"]           # only walk tests/, not the whole repo
python_files   = ["test_*.py"]        # files pytest treats as test files
python_classes = ["Test*"]            # class names that group tests
python_functions = ["test_*"]         # function names that ARE tests

Will run

# tests/test_auth_utils.py
def test_hash_password():
    ...

Won't run

# tests/auth_helpers.py
def check_hash():
    ...
# wrong file prefix AND wrong fn name

Why each line earns its place: testpaths stops pytest from accidentally collecting Alembic versions or example scripts. python_files/classes/functions are the discovery patterns — we keep the defaults but list them explicitly so the convention is visible.

Just Use assert

Pytest rewrites the bytecode of your assert statements so failure messages tell you exactly what was different.

def test_payload_round_trip():
    expected = {"id": 1, "role": "HR"}
    actual   = {"id": 1, "role": "DEV"}
    assert actual == expected
# pytest output:
AssertionError: assert {'id': 1, 'role': 'DEV'} == {'id': 1, 'role': 'HR'}
  Differing items:
  {'role': 'DEV'} != {'role': 'HR'}

No assertEqual, assertIn, assertGreater… One assertion keyword. Pytest figures out the message.

Notice the Duplication?

Look at the three tests you now have. The first line of each looks the same:

def test_verify_password_accepts_correct_password():
    hashed = hash_password("secret123")
    assert verify_password("secret123", hashed) is True

    hashed = hash_password("secret123")

Why this hurts

  • Three tests today — twenty by next week.
  • If we change the password (say, to "hunter2"), every copy has to change.
  • Miss one copy and a test silently lies about what your code does.
  • The setup line is noise — it has nothing to do with what each test is actually checking.

What we want

  • Write the setup once.
  • Every test that needs it gets it — no copy-paste.
  • If the setup changes, we change one line.
  • Each test stays focused on the assertion.

This is exactly what fixtures solve. Next slide: meet them.

Fixtures — Why, How to Define, How to Access

1. The need — duplicated setup hurts

You just saw three verify_password tests, each starting with the same hashed = hash_password("secret123") line. That’s the pattern fixtures fix: tests that need the same starting state, set up over and over.

def test_verify_password_accepts_correct_password():
    hashed = hash_password("secret123")   # setup
    assert verify_password("secret123", hashed) is True

def test_verify_password_rejects_wrong_password():
    hashed = hash_password("secret123")   # same setup, copy-pasted
    assert verify_password("wrong-pass", hashed) is False

Three tests today; ten by next week. If the password changes, every copy must change. Forget one and a test silently lies.

2. How to define a fixture

A function with the @pytest.fixture decorator. It returns (or yields) the value tests will share.

import pytest

@pytest.fixture
def sample_user():
    return {"id": 1,
            "name": "Ada",
            "role": "HR"}

3. How to access it from a test

List the fixture name as a function parameter. Pytest sees the name, calls the fixture, injects the result.

def test_name(sample_user):
    assert sample_user["name"] == "Ada"

def test_role(sample_user):
    assert sample_user["role"] == "HR"

The deal: define once with @pytest.fixture, name it as a parameter wherever you want it. No imports, no manual call, no copy-paste. The next slides go deeper — teardown, scopes, and sharing fixtures across files.

What is a Fixture?

A fixture is a reusable piece of setup. You declare it once, then any test that names it as a parameter gets the result.

import pytest

@pytest.fixture
def sample_user():
    return {"id": 1, "name": "Ada", "role": "HR"}


def test_user_has_a_name(sample_user):           # pytest injects it
    assert sample_user["name"] == "Ada"


def test_user_role_is_hr(sample_user):
    assert sample_user["role"] == "HR"

Mental model: a fixture is a function that returns or yields something. Tests ask for it by parameter name — pytest figures out the dependency graph and runs fixtures in the right order.

Back to Our Tests — Now with a Fixture

Remember the three verify_password tests with the duplicated hash_password("secret123") line? Let’s fix that.

Before — setup copy-pasted
def test_correct_password():
    hashed = hash_password("secret123")
    assert verify_password("secret123", hashed) is True

def test_wrong_password():
    hashed = hash_password("secret123")
    assert verify_password("wrong-pass", hashed) is False

def test_empty_password():

    assert verify_password("", hashed) is False
After — one fixture, injected three times
import pytest
from auth.utils import hash_password, verify_password

@pytest.fixture
def hashed_password():

    assert verify_password("wrong-pass", hashed_password) is False

def test_empty_password(hashed_password):
    assert verify_password("", hashed_password) is False

What changed: the hash is built once in the fixture. Each test names hashed_password as a parameter, and pytest injects the result. Want to change the password? Edit one line. Each test now reads as just the assertion — setup is gone from the body.

Fixtures Can Also Clean Up — Meet yield

So far our fixture just returned a value. That’s fine when the value is a plain Python object — garbage collection cleans up for free. But some fixtures hold something the OS needs to release: a database session, an open file, a network connection.

return — for plain values

@pytest.fixture
def hashed_password():
    return hash_password("secret123")

A string — nothing to clean up. return is enough.

yield — for resources that need cleanup

@pytest.fixture
def something_with_cleanup():
    # SETUP — runs before the test
    yield resource             # ← test runs here
    # TEARDOWN — runs after the test

Hand the value over, then come back to clean up.

Big idea: yield pauses the fixture in the middle. Pytest runs the test, then resumes the fixture after yield — even if the test fails or errors. That’s how we get guaranteed cleanup.

When do we actually need this? The clearest example is testing code that touches a real database. Next slide — let’s see why.

Why In-Memory SQLite for Tests?

Most of our service code takes a db: Session — it needs a real database to do anything useful. But spinning up Postgres for every test is heavy. There’s a much lighter option built right into Python: SQLite, in memory.

Using real Postgres for tests

  • Slow — connect, run migrations, clean up between tests.
  • Shared — one bad test corrupts your dev DB.
  • External — CI needs the Postgres server running too.
  • Hard to reset — tearing down state is fiddly.

Using in-memory SQLite

  • Fast — lives in RAM, no disk, no network.
  • Throwaway — gone the moment the process ends.
  • Zero setup — bundled with Python.
  • Speaks SQL — SQLAlchemy talks to it the same way it talks to Postgres.

The lines that build an async SQLite test database

# `create_async_engine` builds an engine backed by an async driver.
# `async_sessionmaker` is the async-aware factory for ORM sessions.
# `AsyncSession` is the type the factory will hand back to us.
from sqlalchemy.ext.asyncio import create_async_engine, AsyncSession, async_sessionmaker

# `Base` is our app’s declarative base — it tracks every ORM-mapped class
# (Employee, Department, Address, …) on `Base.metadata`. That metadata is
# the "blueprint" we’ll ask SQLAlchemy to materialise as real tables below.
from database import Base


# ── 1. Create the async engine ────────────────────────────────────────
# URL format: dialect+driver://...    →  sqlite + aiosqlite (async driver).
#   - "sqlite://" alone would pick the default sync driver — wrong here.
#   - ":memory:" means "don’t create a file; live entirely in RAM."
# The engine is a long-lived connection pool, not a connection itself.
engine = create_async_engine("sqlite+aiosqlite:///:memory:")


# ── 2. Create every table on the in-memory database ───────────────────
# `engine.begin()` opens an async transactional connection. We need a
# connection (not just the engine) because `create_all` issues real DDL.
#
# Why `run_sync`? `Base.metadata.create_all` is a *sync* SQLAlchemy API —
# there is no `create_all_async`. `run_sync` lets us call sync SQLAlchemy
# code from inside an async connection by hopping onto a worker (via
# greenlet) and hopping back when it’s done. The `await` is on the hop,
# not on `create_all` itself.
async with engine.begin() as conn:
    await conn.run_sync(Base.metadata.create_all)


# ── 3. Build the async session factory ────────────────────────────────
# A factory, not a session — calling it returns a fresh `AsyncSession`.
#
# `expire_on_commit=False` keeps loaded attributes usable after `commit()`.
# Default is True, which marks every loaded attribute as "stale" on commit
# and reloads it on next access. In async tests that becomes an extra
# round-trip we have to remember to `await`, and breaks code that reads
# a refreshed object after committing. Disabling it is the standard
# recommendation for async SQLAlchemy.
TestingSession = async_sessionmaker(engine, expire_on_commit=False)


# ── 4. Open a fresh AsyncSession for the test ─────────────────────────
# This is the object you’ll call `db.add(...)`, `await db.commit()`,
# `await db.refresh(...)`, `await db.scalars(stmt)` on — same ORM API as
# the sync version, just with `await` in front of every IO operation.
db = TestingSession()

What changed vs. sync SQLAlchemy

  • create_engine → create_async_engine
  • URL sqlite:// → sqlite+aiosqlite:// (aiosqlite is the async driver)
  • sessionmaker → async_sessionmaker
  • DDL needs await conn.run_sync(...) — create_all itself is sync, but the connection is async

Caveats

  • SQLite isn’t identical to Postgres — some types and constraints differ.
  • You also need greenlet installed: SQLAlchemy’s async layer uses it to bridge sync ORM internals onto the event loop.
  • For Postgres-only features (native enums, JSONB) or migrations, reach for a Postgres test container.

Using SQLite Manually — No Fixtures Yet (async)

Let’s exercise employee_service with a real async SQLite session. To keep the pain visible, we’ll write it without a fixture first.

# tests/test_employee_service.py

# Async-flavoured SQLAlchemy: async engine factory + async session factory.
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker

# `hash_password` — service.create() drops the password field today, so we
# bypass it and seed the row directly with a valid bcrypt hash ourselves.
from auth.utils import hash_password
# `Base` carries the metadata for every ORM-mapped class — used by
# `create_all` / `drop_all` to build and wipe the schema.
from database import Base
# The service under test.
from employees import service as employee_service
# The ORM model we’ll instantiate to seed a row.
from models.employee import Employee


# `async def` because the body uses `await`. `pytest-asyncio` (mode=auto in
# pyproject.toml) runs this on an event loop for us — no decorator needed.
async def test_get_by_id_returns_seeded_employee():
    # ── SETUP ─────────────────────────────────────────────
    # 1. Build an async engine pointed at an in-memory SQLite database.
    #    The `+aiosqlite` suffix selects the async driver — without it,
    #    SQLAlchemy would pick the default sync driver and refuse to mix.
    engine = create_async_engine("sqlite+aiosqlite:///:memory:")

    # 2. Materialise every ORM table on the empty in-memory DB.
    #    `engine.begin()` is an async context manager that opens a
    #    transactional connection. `create_all` is a *sync* SQLAlchemy
    #    call, so we hand it to `conn.run_sync(...)`, which runs it on a
    #    worker thread (via greenlet) and awaits the result.
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)

    # 3. Build the session factory and immediately open one session.
    #    `expire_on_commit=False` keeps loaded attributes usable after
    #    `commit()` — the recommended setting for async SQLAlchemy.
    db = async_sessionmaker(engine, expire_on_commit=False)()

    # ── ACT ───────────────────────────────────────────────
    # Build an Employee directly (bypassing the service) so we control
    # every field — including `password_hash`, which the service drops.
    seeded = Employee(name="Ada", email="ada@example.com",
                      password_hash=hash_password("secret123"))
    # `add()` is sync — it just stages the row in the session’s identity map.
    db.add(seeded)
    # `commit()` is the IO step — flush + COMMIT to SQLite. Must be awaited.
    await db.commit()
    # `refresh()` re-reads the row so `seeded.id` is populated from the DB.
    await db.refresh(seeded)

    # Call the function under test — it itself is `async def`, so we await.
    fetched = await employee_service.get_by_id(db, seeded.id)

    # ── ASSERT ────────────────────────────────────────────
    # Same id we seeded — proves the lookup returned the right row.
    assert fetched.id == seeded.id
    # Email round-trips through SQLAlchemy unchanged.
    assert fetched.email == "ada@example.com"

    # ── TEARDOWN ──────────────────────────────────────────
    # Close the session — releases the connection back to the pool.
    await db.close()
    # Drop every table so the next test starts clean. (We could also let the
    # engine fall out of scope, but explicit cleanup is the lesson here.)
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.drop_all)
    # Dispose the engine — closes the underlying connection pool.
    await engine.dispose()

Two problems with writing it this way

  • Duplication — every test in this file starts with the same 3 setup lines and ends with the same 2 teardown lines.
  • Leaky teardown — if the assert fails (or anything raises mid-test), the lines below never run. The next test inherits a polluted DB.

What we need

  • Setup written once, shared across tests.
  • Teardown that runs even when the test fails.
  • The test body itself focused only on act and assert.

This is the exact job yield inside a fixture was designed for. Next slide.

Rewriting Our SQLite Test with an Async yield Fixture

Take the manual setup/teardown from the previous slide, lift it into an async fixture, and use yield to split setup from cleanup:

# tests/test_employee_service.py

# `pytest_asyncio` provides the *async-aware* fixture decorator. Plain
# `@pytest.fixture` doesn’t know how to drive an `async def` body — you
# have to use `@pytest_asyncio.fixture` whenever the fixture itself is
# async or yields an async resource.
import pytest_asyncio
# Same async-flavoured SQLAlchemy imports as the previous slide.
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker

from auth.utils import hash_password
from database import Base
from employees import service as employee_service
from models.employee import Employee


# The fixture: a single function that owns the engine, the schema, and
# the session — and tears it all back down when the test finishes.
@pytest_asyncio.fixture
async def db_session():
    # ── SETUP — runs before each test that requests `db_session` ──────
    # Build a fresh in-memory engine. Every test gets its own DB.
    engine = create_async_engine("sqlite+aiosqlite:///:memory:")
    # Open an async transactional connection and create every ORM table.
    # `run_sync` bridges SQLAlchemy’s sync DDL onto the async connection.
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
    # Build the session factory and immediately open one session for the test.
    # `expire_on_commit=False` keeps loaded attrs usable after commit().
    db = async_sessionmaker(engine, expire_on_commit=False)()

    # ── HAND-OFF — pytest pauses the fixture here and runs the test ──
    try:
        yield db                                       # test receives this as the `db_session` arg
    finally:
        # ── TEARDOWN — runs even if the test raised an exception ────────
        # `try / finally` is the guarantee — without it a failing assert
        # would skip the cleanup and the next test would inherit junk.
        # Release the connection back to the engine’s pool.
        await db.close()
        # Wipe the schema. Belt-and-braces — the engine is being disposed
        # next anyway, but explicit cleanup is the lesson here.
        async with engine.begin() as conn:
            await conn.run_sync(Base.metadata.drop_all)
        # Dispose the engine — closes the underlying connection pool.
        await engine.dispose()


# The test is now pure "act + assert" — no engine, no create_all, no
# cleanup. Pytest sees the `db_session` parameter, runs the fixture
# above, and hands the yielded session in.
async def test_get_by_id_returns_seeded_employee(db_session):
    # Seed a row directly via the ORM. We construct Employee ourselves
    # (with a real `password_hash`) because service.create currently
    # drops the password field — bypassing it keeps this test focused.
    seeded = Employee(name="Ada", email="ada@example.com",
                      password_hash=hash_password("secret123"))
    # `add()` is sync — it just stages the row in the session.
    db_session.add(seeded)
    # `commit()` is the IO step. Must be awaited.
    await db_session.commit()
    # `refresh()` re-reads the row so `seeded.id` is populated.
    await db_session.refresh(seeded)

    # Call the function under test — async, so we await.
    fetched = await employee_service.get_by_id(db_session, seeded.id)

    assert fetched.id == seeded.id
    assert fetched.email == "ada@example.com"

How a yield fixture executes — step by step

  1. Pytest sees the test names db_session as a parameter. It calls db_session() and runs everything up to yield — engine, tables, session.
  2. The yielded value (db) is passed into the test. The test body runs.
  3. When the test finishes — pass, fail, or even raise — pytest resumes the fixture function from after the yield. The finally block runs the cleanup.

What we just gained

  • Setup is written once. Every new test just adds db_session as a parameter.
  • Cleanup is guaranteed — try / finally around yield runs the tear-down even if the test crashes.
  • The test body now reads as act + assert only. No engine, no create_all, no close.

What needs yield — and what doesn’t

  • Yes: anything that holds a real-world resource — DB sessions, temp files, network sockets, dependency overrides.
  • No: a plain Python value like hashed_password from earlier. Garbage collection handles those for free — return is enough.

Fixture Scopes

How often a fixture is rebuilt is controlled by its scope. Default is function — rebuilt for every test. That’s what we want for db_session (each test gets a fresh DB). But not every fixture needs to be rebuilt that often.

ScopeBuilt once per…Use for
function (default)each test functionfresh DB session, mutable state
classeach test classshared object across one class
moduleeach test fileread-only data, parser configs
sessionthe entire test runexpensive engine, app config

Example — splitting the engine off as a session-scoped fixture

# tests/conftest.py
@pytest_asyncio.fixture(scope="session", loop_scope="session")
async def engine():
    engine = create_async_engine("sqlite+aiosqlite:///:memory:")   # built ONCE per test run
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
    yield engine
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.drop_all)
    await engine.dispose()


@pytest_asyncio.fixture                                     # default = function scope
async def db_session(engine):                          # fixtures can depend on fixtures
    db = async_sessionmaker(engine, expire_on_commit=False)()
    try:
        yield db
    finally:
        await db.close()

The loop_scope bit: when an async fixture is widened past function, pytest-asyncio needs to know which event loop it lives on. Set loop_scope equal to (or wider than) the fixture scope so every consumer sees the same loop. Forget it and you’ll get "attached to a different loop" errors at runtime.

Trade-off: wider scope = faster (less rebuilding) but more leakage risk between tests. Default to function; widen only when the resource is read-only or expensive to build. The engine is fine at session — we wipe and recreate the tables per test, the engine itself is just a connection pool.

Testing Code That Should Raise

Sometimes the right behaviour is an exception — e.g. looking up an employee that doesn’t exist, or rejecting an empty name. How do we test that?

The naive way (don’t do this)

def test_divide_by_zero():
    try:
        divide(10, 0)
        assert False, "expected ZeroDivisionError"
    except ZeroDivisionError:
        pass            # OK, that’s what we wanted

Works, but verbose — and easy to forget the assert False, in which case a missing exception silently passes the test.

The pytest way

import pytest

def test_divide_by_zero():
    with pytest.raises(ZeroDivisionError):
        divide(10, 0)

Read it like English: "with pytest expecting a ZeroDivisionError — do this." If the block raises that exception, the test passes. If it raises something else, or doesn’t raise at all, the test fails.

A Real Example — and Inspecting the Error

Now that we have db_session in conftest.py, this slots in naturally. Look up an employee that doesn’t exist — we expect NotFoundException.

# `pytest` (not `pytest_asyncio`) is what provides `pytest.raises`. The two
# libraries cooperate — pytest is the framework; pytest-asyncio is a plugin
# that adds async-fixture support. You never swap one for the other.
import pytest

# Our domain exception — raised by the service when a row is missing.
from exceptions import NotFoundException
# The function under test.
from employees import service as employee_service


# `async def` because the body uses `await`. The `db_session` fixture comes
# from `conftest.py` — pytest-asyncio drives this on the event loop for us.
async def test_get_by_id_raises_when_missing(db_session):
    # Step 1: the exception itself
    # `pytest.raises(...)` is a context manager that *expects* the block to
    # raise the given exception. If it does → test passes. If it raises
    # something else → test fails. If it raises nothing → test fails too.
    # `as exc_info` captures a handle on the raised exception for later checks.
    with pytest.raises(NotFoundException) as exc_info:
        # `get_by_id` is `async def`, so we `await` it. The `await` lives
        # *inside* the `with` block — that’s the call we expect to raise.
        await employee_service.get_by_id(db_session, 9999)

    # Step 2: details about the exception
    # `exc_info.value` is the actual exception object (a NotFoundException).
    # Our base `AppException` exposes `.detail` — we assert the missing ID
    # appears in it, locking in "this exception with this content", not just
    # "some NotFoundException was raised somewhere".
    assert "9999" in exc_info.value.detail

What the test guarantees

  • get_by_id with a missing ID must raise NotFoundException.
  • The message must mention the ID (so users know what was missing).

What is exc_info?

  • The handle pytest gives you on the raised exception.
  • exc_info.value is the exception object itself.
  • exc_info.value.detail is just our AppException’s detail string.

Why bother asserting the message? If the test only said "some NotFoundException was raised", a future bug that raised it with the wrong ID would still pass. Asserting on the detail locks in the contract: this exception, with this content.

FastAPI TestClient

What is TestClient?

A client that calls your FastAPI app in-process, no HTTP server needed.

Without TestClient

  • Start uvicorn on a port
  • Spawn a real HTTP request
  • Tear down the server
  • Slow, flaky, hard to debug

With httpx.AsyncClient + ASGITransport

  • Calls your app object directly via ASGI
  • Same routes, dependencies, exception handlers
  • Async API: await client.get(...), await client.post(...)
  • Fast and deterministic; stays on the same event loop as the app

Why this matters: you can write tests that look exactly like real HTTP calls — same status codes, same JSON bodies — without the cost of running a real server.

Why AsyncClient and not TestClient? Every route in this app is async def. TestClient is built on httpx but exposes a sync API — it shells the call into a thread under the hood. AsyncClient keeps the test body on the same event loop as the app, so await client.get(...) reads exactly like the production code.

  • How to use it — the client fixture (next slide) hands you an AsyncClient already wired to the app. Test body is async def; every call is await client.<verb>(...).

Overriding the DB Dependency for AsyncClient

The db_session fixture in conftest.py gives each test a fresh async SQLite session. Routes call get_db() via FastAPI’s dependency system — that path doesn’t know about our fixture. app.dependency_overrides is the bridge.

What app.dependency_overrides is

  • A dict on the FastAPI app.
  • Keys: the original dependency function (get_db).
  • Values: the replacement — since get_db is an async generator, the override must be one too.
  • Cleared at the end so the next test isn’t affected.

Why a separate client fixture

  • Unit tests just need db_session — no HTTP.
  • HTTP tests need both: a session for setup, and an AsyncClient whose routes use that same session.
  • The client fixture wires the two together.
# tests/conftest.py — adding the client fixture alongside db_session
import pytest_asyncio
from httpx import AsyncClient, ASGITransport
from database import get_db
from main import app


@pytest_asyncio.fixture
async def client(db_session):
    async def _override_get_db():
        yield db_session                                       # async generator, matches the real get_db

    app.dependency_overrides[get_db] = _override_get_db     # every route now sees the test session
    transport = ASGITransport(app=app)                       # httpx talks to ASGI in-process, no socket
    async with AsyncClient(transport=transport, base_url="http://test") as c:
        yield c
    app.dependency_overrides.clear()                       # reset for the next test

The same trick works for any dependency. Fake the current user, the JWT decoder, a third-party HTTP client — add another entry to app.dependency_overrides. Same pattern, same teardown.

Mocking

Now we test our airbag — auth_service.login() — without spinning up a real database.

Replace the repository with a mock. Verify the right method was called. Confirm the right token was minted. No SQLite, no Postgres, no network.

When to Mock (and When Not To)

Mock when…

  • The dependency is slow / flaky (network, S3, payments).
  • It's non-deterministic (time, randomness, UUIDs).
  • You're testing interactions ("did we call send_email?").
  • You want to simulate a failure that's hard to reproduce (DB down).

Don't mock when…

  • The collaborator is cheap and deterministic (in-memory SQLite).
  • You'd be re-implementing the thing you're trying to test.
  • The mock setup is longer than the test it enables.

Smell: if your mocks need to be updated every time the implementation changes, you're testing the implementation instead of the behaviour. Pull back — let real code do real things where it's cheap.

Meet monkeypatch

Pytest ships with a built-in fixture called monkeypatch that lets you temporarily replace an attribute, environment variable, or function for the duration of a test. When the test ends, pytest restores the original automatically — no cleanup, no leaks.

What it’s for

  • Avoid hitting the network, DB, or file system during a test.
  • Replace a function’s return value with a known fake.
  • Set / unset environment variables safely.

The 3 calls you’ll use

  • monkeypatch.setattr(target, value)
  • monkeypatch.setenv(name, value)
  • monkeypatch.delenv(name)

Mental model: "for this one test, pretend X is Y." When the test finishes, pytest puts X back to what it was.

Example 1 — Mocking an Environment Variable

Our app reads JWT_SECRET from the environment. In a test, we don’t want to depend on the real secret — just provide a fake one.

import os

def test_jwt_secret_is_read_from_env(monkeypatch):
    monkeypatch.setenv("JWT_SECRET", "test-secret-123")

    assert os.getenv("JWT_SECRET") == "test-secret-123"
    # …call the function that reads JWT_SECRET and assert its behaviour

After the test: JWT_SECRET goes back to whatever it was (or unset). The next test sees a clean environment — guaranteed.

Example 2 — Mocking a Function Response

The login service calls employee_repo.get_by_email(...) which hits the database. In a unit test we want to skip the DB entirely and just return a fake employee.

from employees.models import Employee, EmployeeRole
from auth import service as auth_service

def test_login_returns_token(monkeypatch):
    fake_employee = Employee(
        id=1, name="Ada", email="ada@example.com",
        password_hash=hash_password("secret"),
        role=EmployeeRole.HR,
    )

    monkeypatch.setattr(
        "auth.service.employee_repo.get_by_email",
        lambda _db, _email: fake_employee,
    )

    token = auth_service.login(db=None,
                                email="ada@example.com",
                                password="secret")
    assert isinstance(token, str) and token

Read it like this: "for this test, when auth.service calls employee_repo.get_by_email, return fake_employee instead." No DB, no real lookup — just the behaviour we want to test.

Tip: patch where the function is used, not where it’s defined. We use "auth.service.employee_repo.get_by_email" because auth.service is the module that imported it.

Why a plain lambda still works here: auth_service.login() is itself a sync function — it calls employee_repo.get_by_email(...) synchronously and uses the return value directly. A sync stub matches. When the caller is async and awaits the dependency, the stub must return an awaitable — that’s when you reach for AsyncMock (next slide).

Example 3 — Mocking an async Dependency with AsyncMock

Our repository is async: department_repo.get_by_id(...) is async def. The service awaits it. A plain Mock returns a Mock object — await on that explodes. AsyncMock from unittest.mock returns an awaitable, so the service can await it like the real thing.

import pytest
from unittest.mock import AsyncMock

from departments import service as department_service
from exceptions import NotFoundException


async def test_service_raises_when_repo_returns_none(monkeypatch):
    monkeypatch.setattr(
        "departments.service.department_repo.get_by_id",
        AsyncMock(return_value=None),           # awaitable that resolves to None
    )

    with pytest.raises(NotFoundException):
        await department_service.get_by_id(db=None, department_id=1)

Why this matters

  • No SQLite needed — pure service logic test.
  • Proves the service’s "missing ⇒ raise" branch deterministically.
  • Runs in microseconds.

Mock vs AsyncMock

  • Mock(return_value=42) — call returns 42 (not awaitable).
  • AsyncMock(return_value=42) — call returns a coroutine that resolves to 42.
  • Use AsyncMock whenever the caller does await mock(...).

👉 In Our Employee Management Project

  • Open tests/handson_solutions/session2_solution.py::test_service_raises_when_repo_returns_none — this is the canonical example.
  • Try this now: swap AsyncMock for plain Mock and watch the failure (TypeError: object Mock can't be used in 'await' expression). That error is your hint that the target is async.

Mocking Recap

Do

  • Use monkeypatch — pytest’s built-in, auto-restored.
  • Mock anything slow / flaky / external (DB, network, email).
  • Patch where the function is used, not where it’s defined.
  • Keep the mock setup small — one or two lines.

Avoid

  • Mocking everything — you end up testing the mock.
  • Mocking cheap, deterministic things (an in-memory SQLite session).
  • Rebuilding the same mock in 20 tests — promote it to a fixture.
  • Forgetting to assert that the mocked function was actually called.

Python also has unittest.mock.Mock, AsyncMock, and patch for more advanced cases. For this project: monkeypatch swaps the binding, AsyncMock wraps async dependencies, and patch scopes a swap to a with block.

Integration Testing

Beyond Unit Tests

What integration tests check

That multiple components work together correctly:

  • Route → service → repository → database.
  • Auth dependency → role checker → route.
  • Pydantic validation → exception handler → HTTP status.

What we already have

tests/test_employees_api.py uses httpx.AsyncClient + ASGITransport + in-memory SQLite (via aiosqlite) to integration-test the whole HTTP slice.

  • Fast (milliseconds per test).
  • Hermetic (no shared state across runs).
  • Real code paths — only get_db is overridden.

Where SQLite is not enough: migrations, Postgres-only features (native enums, JSONB), or anything that exercises database-driver behaviour. For those, real-service tests (covered next) take over.

End-to-End (E2E) Testing

E2E tests check the whole product from the user’s perspective — real browser, real backend, real database. They sit at the top of the test pyramid: most expensive, but the closest thing to real-world confidence.

Why E2E matters

  • Catches bugs at the seams between systems (frontend ↔ backend ↔ DB).
  • Verifies the user journey actually works (login → create employee → see them in the list).
  • Highest confidence before a release.

The trade-off

  • Slow — seconds per test.
  • Brittle — UI changes break them often.
  • Hard to debug when they fail.
  • Run a small handful, not hundreds.

Common tools

  • Playwright, Cypress, Selenium — for browser-driven E2E tests.
  • Postman / Newman — for API-level E2E flows.
  • Testcontainers — spins up real Postgres/Redis in Docker when SQLite isn’t enough.

For this training: we focus on unit + integration tests with pytest and TestClient. E2E is good to know about — you’ll meet it on real projects.

Recap & Best Practices

Best Practices

Do

  • Name tests after the behaviour, not the function.
  • Arrange → Act → Assert. Three blocks, in that order.
  • One logical assertion per test (multiple asserts are fine if they describe one outcome).
  • Make tests independent — no test should depend on another's output.
  • Use fixtures + factories to keep test bodies short.
  • Test edge cases: empty inputs, max values, missing fields, wrong roles.

Don't

  • Don't test the framework (FastAPI, SQLAlchemy) — test your code.
  • Don't share mutable fixtures across tests without scoping.
  • Don't sleep / wait in tests — mock time instead.
  • Don't commit a .skip without a tracked reason.
  • Don't print — assert.
  • Don't chase 100% coverage at the cost of meaningful assertions.

Key Takeaways

1. Test the airbag, not the whole car

Unit tests in isolation, with mocks. Catch defects before integration. Cheaper and faster than smashing the car.

2. Pytest is just def test_*(): + assert

Discovery by convention. Plain assertions with rich failure messages. Zero boilerplate. Fixtures for reuse.

3. TestClient + dependency_overrides

HTTP-shaped tests against your real app. Swap get_db for an in-memory SQLite session. Reach for test containers when SQLite would lie.

4. Mock with monkeypatch

Replace external calls (DB, network, env vars) with fakes for the duration of a test — auto-restored when the test ends. Patch where the function is used.

5. Tests are part of the contract

Cover route → service → repo flow. Auth & roles. Validation. Error paths. Coverage is a tool, not a target.
